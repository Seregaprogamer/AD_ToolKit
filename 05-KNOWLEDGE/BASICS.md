# Как читать раунд Attack–Defense

**Сервис** — приложение команды с определённым интерфейсом и хранилищем. Клиент может пройти путь «создать запись → получить ID → прочитать запись по ID». Команды могут получить одинаковый исходный код, но у каждой своё состояние.

**Checker** — клиент организаторов. В типичном цикле он проверяет обычную функцию сервиса, записывает контрольные данные и позже запрашивает их обратно. **Flag** — уникальная строка среди этих данных. Для защиты важно, чтобы действительные данные оставались доступны через предусмотренную функцию. Заменить базу вчерашней копией — значит потерять записи, созданные с тех пор.

**Tick / раунд** — интервал учёта состояния и очков. Следующая проверка может наступить позднее твоей правки. Сопоставляй время запроса, логи и номер обновившегося раунда. **SLA** характеризует доступность и корректность работы по данным проверок. Формула и названия статусов зависят от платформы. Время раунда и срок жизни записей бери с брифинга.

**Как устроена площадка.** Ноутбук команды, игровой сервер с твоими сервисами, проверяющая система и табло — разные узлы. `localhost` на ноутбуке не проверяет порт игрового сервера. На Linux-хосте контейнер имеет собственную сеть, а в Compose база обычно доступна по имени сервиса. Вначале подпиши, где именно открыт каждый терминал.

**Как читать статусы.** Нет соединения — проверь адрес, маршрут и слушающий порт. Есть ответ, но отличается формат — проверь версию интерфейса. Новая запись читается, старая пропала — проверь подключённую БД, volume и миграцию. Если локально всё прошло, дождись результата следующей проверки.

**Ошибка новичка** — трое одновременно редактируют конфиг, перезапускают БД и меняют порт. На сервис назначьте одного исполнителя. Остальные читают логи, записывают время и повторяют проверку. Один цикл работы — одна гипотеза, одно изменение, одна проверка.

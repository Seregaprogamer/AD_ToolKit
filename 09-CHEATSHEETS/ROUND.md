# Команды на один раунд

Из каталога нужного Compose-проекта. Вместо APP подставь имя из первой команды.

| Нужно узнать | Команда | Смотри на |
|---|---|---|
| Какие есть сервисы | `docker compose config --services` | Имена для остальных команд |
| Что упало | `docker compose ps -a` | State, Exit, Ports |
| Первая ошибка | `docker compose logs --timestamps --since 5m --tail 160 APP` | Событие **до** рестарта |
| Что слушает хост | `ss -lntp` | Локальный адрес и порт |
| Как выбран маршрут | `ip route get АДРЕС_СВОЕГО_СЕРВИСА` | dev, src, via |
| Код и задержка | `curl -so /dev/null --connect-timeout 2 --max-time 4 -w '%{http_code} %{time_total}\n' http://127.0.0.1:18765/health` | HTTP 000 — ответа HTTP нет |
| Ресурсы | `docker stats --no-stream`, `free -h`, `df -h`, `df -i` | Память, место, inode |
| Откат | [[07-BACKUPS/README\|Порядок действий]] | Код/конфиг и свежие данные учитываются отдельно |
| Проверка после изменения | Старая запись → создать новую → прочитать → следующий tick | Исправен весь сценарий |

## Какие уязвимости могут встретиться в игровых сервисах

Наличие конкретной ошибки определяется кодом и контрактом выданного сервиса. Название шаблона само по себе ничего не говорит о сервисе соперника.

**Темы уже разобранных 11 шаблонов.** SQL- и NoSQL-инъекции, SSTI, SSRF, XSS и CSRF, выход за пределы файлового каталога, IDOR, гонки, недоверенная десериализация pickle, небезопасный выбор функции через globals и CRC32 в роли секрета. Ниже — дополнительные случаи для ревью логики сервиса.

| Класс ошибки | Пример нарушения контракта | Что смотреть в коде своей копии |
|---|---|---|
| Массовое присваивание полей | Форма редактирования профиля должна менять только имя, но обработчик копирует все поля запроса в модель, включая роль. | Список разрешённых для записи полей у каждой операции. Внутренние поля задаёт сервер. |
| Раскрытие лишних полей | Список публичных заметок показывает только заголовки, но API отправляет в JSON также приватный текст. | Схему ответа и сериализатор. Скрытие поля в интерфейсе не удаляет его из сетевого ответа. |
| Ошибка доступа к функции | Владелец вправе читать свою заявку, но утверждать заявки может только модератор. Проверка владельца не отвечает на вопрос, кому разрешено утверждение. | Проверку роли для каждой привилегированной операции. Обычный пользователь должен сохранить право читать свою заявку. |
| Смешение пользователей в кэше | Обработчик профиля проверяет сессию, но общий кэш сохраняет персональный ответ под одним ключом для всех пользователей. | Правила кэширования приватных ответов на уровне приложения и прокси. Две учебные учётные записи должны получать каждая свой профиль. |
